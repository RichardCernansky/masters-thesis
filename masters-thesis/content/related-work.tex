Chapter~\ref{chapter:sota} described the field as a whole. This chapter is narrower and covers only the
works from which the model studied in this thesis is assembled. It begins with the query-based formulation
that the model inherits, continues with the components introduced by the \ac{lidar} branch, and closes with
the two works that preceded this thesis in taking ViP3D as the base model and extending it with the
\ac{lidar} modality.


\section{Query-Based Detection and Tracking}
\label{sec:rw-queries}

% DETR -> Deformable DETR -> DETR3D -> MOTR, ending at ViP3D as the baseline this work extends
The architecture studied here descends from a line of work that removed many hand-designed components
like \ac{nms} procedure or anchor generation. DETR \cite{Carion2020DETR} formulates detection as the 
direct prediction of a fixed-size set of object, in which a small number of learned queries attend to 
the image features and a Hungarian matching assigns every query to at most one annotated object.  

The slow convergence caused by every query attending to every pixel was addressed by Deformable DETR
\cite{Zhu2021DeformableDETR}, which lets a query sample only a few learned offsets around a reference
point and thereby reduces both the cost and the number of epochs required for training. The reference
point of a query is obtained by a linear projection of the positional part of its embedding, followed by
a sigmoid that maps it into normalised coordinates.
In the same work the authors introduce a two-stage variant that initialises the reference points from the
centres of the highest scoring region proposals generated on top of the encoder output, so that the decoder
starts from positions determined by the input rather than by a learned constant, and this variant
outperforms the single-stage one \cite{Zhu2021DeformableDETR}.
DETR3D carried the formulation into three dimensions by placing the reference point of each query in 3D space and projecting
it into the available camera views, so that multi-view images are consumed without an intermediate dense
depth estimate \cite{Wang2021DETR3D}.

The step from detection to tracking was taken by MOTR, which keeps a query alive across frames instead
of detecting the same object independently in each one. The identity of an object is then carried by the
query itself rather than recovered afterwards by an association heuristic \cite{Zeng2022MOTR}. How reliably
that identity survives across frames is what the tracking metrics of
Section~\ref{subsec:sota-metrics-track} measure. ViP3D
combines the two ideas and extends them to forecasting. Agent queries are initialised in the DETR3D
manner, propagated through time in the MOTR manner by a memory bank and a query interaction module,
and read directly by the trajectory decoder. The result is a pipeline that is differentiable from the
camera images to the predicted trajectories and that contains no thresholded intermediate representation
\cite{Gu2023ViP3D}. ViP3D is the model this thesis builds upon.



\section{LiDAR Backbones and Heatmap Query Initialisation}
\label{sec:rw-lidar}

ViP3D perceives the scene through cameras alone, so its queries are initialised from a fixed learned
embedding that is identical in every frame regardless of what the scene contains. Replacing that embedding
requires a representation of the point cloud and a way of reading object hypotheses out of it.

The representation follows the established encoders described in
Section~\ref{subsec:sota-dl}. PointPillars groups the points into vertical columns and flattens them into a
pseudo-image, which allows a conventional two-dimensional backbone to process the point cloud at a cost
that does not depend on its density \cite{Lang2019PointPillars}, and SECOND forms the \ac{bev} feature map
with sparse convolutions that skip the empty regions of the grid \cite{Yan2018SECOND}.

The hypotheses come from CenterPoint, which abandons anchors and instead predicts a class-wise heatmap over
the \ac{bev} grid, where every peak marks the centre of an object \cite{Yin2021CenterPoint}. TransFusion \cite{Bai2022TransFusion}
turned this into the initialisation of a transformer decoder. \emph{The highest scoring heatmap peaks become
object queries whose content is sampled from the \ac{bev} feature} at the peak and whose reference point is
the metric position of that cell, so that the decoder begins from a hypothesis that depends on the input
rather than from a constant embedding. \emph{This is the mechanism that replaces the
learned query embedding of ViP3D in the present work.}


\section{Attention-Based Camera-LiDAR Fusion}
\label{sec:rw-fusion}

% TransFusion second stage, SMCA, and Lift-Splat-Shoot as the opposite projection direction

After the queries originate from the point cloud \ref{sec:rw-lidar}, the camera modality may be introduced
to supply the colour and texture that the point cloud does not contain. TransFusion \cite{Bai2022TransFusion} 
performs this both in the initialization procedure and by adding a second decoder layer that cross-attends to the image features by projecting the queries' 
location into image plane like \cite{Zhu2021DeformableDETR}. It trains that layer on top of a frozen \ac{lidar} model,
which prevents the fusion from destabilising a branch that was already pretrained beforehand. The attention in that 
layer is spatially modulated following SMCA \cite{Gao2021SMCA}, which adds the logarithm of a Gaussian
centred on the projection of the reference point of the query to the attention logits before the softmax, 
so that a query attends only where it can geometrically be and converges considerably faster than
unconstrained cross-attention.

The initialisation itself operates in the \ac{bev} plane rather than in the image. TransFusion collapses
the features of each image along the vertical axis, so that one image column becomes a single token, on the
observation that a \ac{bev} location maps to a column by camera geometry and that a column rarely holds
more than one object. The \ac{bev} cells then attend to those columns, the result is averaged over the
cameras, and a second heatmap predicted from it is combined with the \ac{lidar} one, so that the camera
takes part in deciding which queries are created at all. 

\section{Trajectory Decoding from Agent Features}
\label{sec:rw-decoding}

% VectorNet, LaneGCN, and how ViP3D differs by decoding from query features

The last stage turns the state of an agent into a set of possible futures. VectorNet replaced the
rasterised scene encodings common at the time with a vectorised one, in which agent histories and map
elements are represented as polylines and a hierarchical graph aggregates first within and then across them
\cite{VectorNet2020}. LaneGCN refined the treatment of the map by building an explicit lane graph and
exchanging information between the agents and the lanes in both directions \cite{Liang2020LaneGCN}. The
decoder of ViP3D follows this line, with one substantial difference. It does not receive an observed
trajectory assembled by a tracker, but the feature vector of the agent query itself, which still carries
the visual evidence that a bounding box would have discarded \cite{Gu2023ViP3D}.


\section{Positioning of This Work}
\label{sec:rw-positioning}

% Li-ViP3D, Li-ViP3D++, and the gap this thesis addresses

The idea of giving ViP3D a \ac{lidar} branch has been pursued before in the group in which this thesis was
written. Li-ViP3D \cite{Halinkovic2025LiViP3D} addresses limited capability of exploitation of the complementarity
between camera and \ac{lidar} data in the current \ac{pnp}
solutions by extending ViP3D query-based camera-only pipeline with camera-\ac{lidar} fusion and reports improved
end-to-end perception and prediction on nuScenes. Li-ViP3D++ \cite{Halinkovic2026LiViP3DPP} develops the
fusion further by gating the contribution of the camera on the query and by sampling the image features
in deformable manner. Both of these works treat the addition of \ac{lidar} as a fusion problem, in which the two
modalities are combined for queries that are still generated the way ViP3D generates them from a learned embedding 
that never depends on any particular scene. 

The present work asks where the queries should come from and tackles the problem of their initialisation. 
As mentioned in \ref{sec:rw-queries}, Deformable DETR \cite{Zhu2021DeformableDETR} indroduced a two-stage variant 
initialises the reference points from the centres of the highest scoring region proposals generated
on top of the encoder output, so that the decoder starts from positions determined by
the input. This variant outperformed the single-stage one, which is evidence that reference points derived from the data
are prefereable to reference points learned as constants. 
In this thesis, the same principle was applied in the \ac{bev} plane. The proposal generator is a class-wise heatmap
predicted from the \ac{lidar} feature map, and its highest scoring peaks supply the query with both the 
reference point from the metric position of the peak and the content from the feature sampled at that cell.

This work is therefore positioned differently from the two that precede it. Li-ViP3D and Li-ViP3D++ combine
the two modalities for queries that are still created the way ViP3D creates them, so the \ac{lidar} enters
at the moment a query is refined. Here it enters earlier, at the moment a query is created, and the camera
is reintroduced only afterwards in a second decoder layer trained on top of the frozen \ac{lidar} model.
Fusion is thus a refinement of a hypothesis that the point cloud has already formed.

\section{Summary and Starting Points}
\label{sec:summary}

Based on the study presented in Chapters~\ref{chapter:sota} and~\ref{chapter:related}, the following gaps are identified with potential to improve:
\begin{itemize}
    \item Query-based \ac{pnp} models still create their queries from a learned embedding that is identical in every frame,
          although the detection literature has already shown that reference points derived from the input outperform 
          reference points learned as constants.
    \item The works that add \ac{lidar} to ViP3D use it to refine queries rather than to create them, so it is not known 
          what the query-based formulation achieves when the queriese themselves originate in the point cloud. 
    \item A query that already begins at a position read from the point cloud has little left to correct, which should allow
          a far shallower decoder. ViP3D moves its queries towards the objects through several refinement layers, whereas an
          initialisation of this kind leaves only the camera layer to refine. The latency this saves and the accuracy of predictions
          it costs have not been measured. 
    \item The contribution of the camera has been measured only on top of camera-initialised models, 
          so it remains unclear which metrics and which object classes still benefit once the queries already carry
          geometric evidence.
\end{itemize}

The goal of this thesis is therefore to develop and evaluate a deep learning architecture for end-to-end perception and
prediction in which the agent queries originate in the point cloud, extending ViP3D with a \ac{lidar}
branch in place of its learned query embedding.

To fill in these gaps, the following starting points are proposed.
\begin{itemize}
    \item Starting point 1: replace the learned query embedding of ViP3D with a class-wise heatmap
    predicted from the \ac{lidar} \ac{bev} feature map, taking the reference point of a query from the
    metric position of a peak and its content from the feature sampled at that cell.
   \item Starting point 2: reintroduce the camera as a single refinement layer with spatially modulated
    cross-attention, trained on top of the frozen \ac{lidar} model, and ablate it so that the effect of
    the fusion can be evaluated separately.
    \item Starting point 3: reduce the decoder to one layer reading the \ac{bev} map and that one camera
    layer, and report the metrics against measured latency so that the saving attributable to the
    initialisation is separated from the cost of less refinement.
\end{itemize}
